# Homologação isolada do WAND METHOD

## Diagnóstico e escolha

A referência da preparação é `10ab86a` na `dev/design-system-global`. O GitHub é público e a branch padrão é `main`. O workflow versionado executa testes em Node.js 22 em pushes na main, em PRs e por acionamento manual. O `CNAME` aponta para o domínio oficial. O workflow inspecionado não contém deploy. A origem configurada no painel GitHub Pages não foi verificada nesta rodada.

O aplicativo estático contém o endereço de produção em páginas e scripts. A função `wand-enviar-contrato` usa Resend e tem fallback para a URL oficial. O Supabase conectado listou somente o WAND METHOD de produção, com Postgres 17. A inspeção usou histórico de migrações e consultas de catálogo em transações somente leitura, sem selecionar linhas de alunos, usuários ou contratos. O repositório tem migrações incrementais e scripts históricos, mas não tem configuração local nem o DDL completo da base.

Na preparação inicial, a opção foi Supabase CLI local, com Docker, Postgres, Auth, Storage e Mailpit. Não requer projeto adicional nem cobrança do Supabase. O workspace tem o cliente Docker, mas o comando `docker info` recebeu permissão negada no daemon. Para execução integral no Cloud, use um ambiente autorizado com daemon acessível ou, se isso for inviável, um projeto separado no plano Free após confirmar disponibilidade e obter autorização. Abrir um projeto adicional não resolve a ausência do esquema-base. [Supabase local](https://supabase.com/docs/guides/local-development) · [Planos Supabase](https://supabase.com/pricing)

## Preparação local

1. Usar um perfil de navegador limpo e um diretório Supabase exclusivo fora do checkout. Instalar uma versão fixa da CLI em ambiente com Docker acessível. Conferir `supabase --version`, `supabase init --help` e `supabase start --help`. Inicializar e iniciar só nesse diretório. Não usar link de projeto remoto. Confirmar API em `http://127.0.0.1:54321`, banco local e Mailpit da pilha. Ao preparar Auth, permitir redirecionamento apenas ao app local em `http://127.0.0.1:4180`, incluindo o caminho de recuperação de senha.
2. Validar o artefato estrutural, confirmar que a conexão aponta ao banco descartável e só então restaurar a base e os incrementos necessários. Conferir o baseline, as permissões e a lista final de migrações locais. Usar dados de teste gerados localmente.
3. Criar no Auth local `coach@wand.test`, `aluno-a@wand.test` e `aluno-b@wand.test`. Gerar senhas únicas e guardar fora do Git. Usar os IDs do Auth para os registros de `profiles`, com `role=admin` somente para o coach e `role=aluno` para os demais. O papel administrativo deve ser atribuído pela configuração privilegiada local, preservando os triggers. Inserir dois registros de `alunos` com `user_id`, e-mail fictício, nome sintético, `Status=Ativo` e modalidade de teste. Deixar o ID numérico a cargo da identidade do banco.
4. O esquema atual de `alunos` não tem coluna de treinador e a política observada de administrador é global. Definir A como titular dos registros sintéticos criados pelo coach e B como aluno de controle, sem registros vinculados a esse coach. B deve ficar impedido de acessar os registros de A. Para testar isolamento **entre treinadores**, acrescentar um segundo coach de controle e usar os vínculos que cada recurso realmente grava. Se algum recurso for global para administradores e a regra aprovada exigir vínculo individual, registrar a divergência como bloqueio, sem mascarar o resultado com uma RLS diferente da candidata.
5. Injetar `WAND_LOCAL_PUBLIC_KEY` pelo runtime local e iniciar `python3 scripts/homologacao-local.py`. O script serve uma cópia temporária em loopback, reescreve URL e chave do Supabase nas páginas, substitui redirecionamentos oficiais e links de WhatsApp, desativa o service worker e aplica CSP. Usar somente a chave pública da pilha local no cliente. A chave privilegiada, quando necessária para preparar dados fictícios, fica no processo administrativo local. O script usa dependências web do CDN permitido, portanto pode exigir acesso ao CDN para carregar os módulos do cliente.
6. Para Auth, usar Mailpit. Para o envio de contratos, é preciso preparar uma cópia local da função `wand-enviar-contrato` com remetente e destinatários de teste, URL local e transporte exclusivo para um coletor local. O código versionado chama Resend diretamente. Até preparar e verificar esse transporte, manter o envio externo desligado e classificar o envio de contrato como pendente. Web Push, CAPTCHA e vídeo externo também não fazem parte da prova local sem configuração isolada própria.

## Provas de isolamento e roteiro funcional

Antes de cadastrar dados, confirmar que os endpoints de API, banco, Auth, Storage, funções e e-mail pertencem à pilha local. A cópia preparada deve falhar se restarem referências de produção conhecidas. Usar bloqueio de rede também para navegação externa e para o processo de funções. CSP restringe recursos e conexão do navegador, mas não substitui restrições de rede do backend. Sem chaves, sessões ou destino de produção no runtime, testar o bloqueio contra um domínio sentinela fictício, sem enviar pedidos de teste ao domínio real. Guardar somente métricas e URLs sem tokens.
